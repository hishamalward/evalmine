This page preserves the v2 audit and implementation record as it stood on 25 August 2026. Test counts, model comparisons, and operational notes are dated evidence, not current setup guidance. Use the repository README and specification for the current product contract.

Repository audit · product reframe · interface concepts

Keep the evidence engine.
Rebuild the laboratory.

evalmine is a careful, credible evaluator for stateless API answers. Your real need is a controlled experiment system for whole agents working inside isolated versions of your environment—sometimes for one response, sometimes across a long conversation, and sometimes as a domain pipeline.

Recommendation

Do not throw away v1. Do not extend its current core in place.

Preserve the judge calibration, blinded human review, raw artifacts, cost discipline, HTML reporting, and decision log. Introduce a v2 experiment model whose unit is an arm running an episode in a workspace, not a model answering a prompt. Keep the old prompt runner as one runner type.

02 / Original system

What v1 did at the time of the audit

This is the historical baseline that motivated v2. The repository now also includes the complete experiment spine, subscription runners, validators, blind labeling, calibrated episode judging, decision HTML, workflow DAG, and MCP control plane shown below.

The important boundary: the adapter protocol is complete(Request) → Response. There is no workspace, tool loop, repository diff, session, follow-up turn, plugin set, agent instruction discovery, task DAG, or environment snapshot in the data model.

Keep nearly intact

  • Position-swapped, model-blind pairwise judging
  • Cohen’s kappa gate against your labels
  • Raw answer/pair artifacts and reproducible reports
  • Self-contained HTML with blind A/B labeling
  • Cost caps, unknown-price failure, dated prices
  • Decision log separated from measurement

Replace or generalize

  • model becomes an arm with runner + model + config
  • task/case becomes an episode with turns + validators
  • API adapter becomes a runner protocol for CLIs and pipelines
  • Answer cache becomes immutable run artifacts + explicit replay
  • Code-block checks become validators against the workspace
  • Serial nested loops become a dependency-aware scheduler

04 / Experimental control

The experiment is invalid if the timelines touch

Your bias concern has two separate sources: repository state contamination and agent/session contamination. Both need explicit isolation.

Failure mode

A worktree alone is not the control

It separates checked-out files, but agent home configuration, session history, global memory, hooks, caches, and external services may still be shared. The run manifest must say which are isolated, shared read-only, or deliberately uncontrolled.

Follow-ups

Mirror the protocol, not accidental wording

For fair multi-turn tests, pre-script common follow-ups or define conditional follow-up rules from deterministic workspace probes. Human-steered arms should remain blind and record why a follow-up diverged.

Long horizon

Parallel timelines are allowed to diverge

A “respectable body of work” becomes a longitudinal cohort. Each arm receives the same sequence of task intents, keeps its own prior changes, and is evaluated on compounding quality—not forced back into identical state after every task.

05 / v2 product model

Four experiment types, one evidence envelope

Separating experiment types prevents the report from making stronger claims than the design supports.

Model swap

Same agent product, same config

Example: Claude Code with Opus 5 vs 4.8 vs 4.6.

Claim allowed: model choice changed the observed result inside this product harness.
Config ablation

Same model, instructions/plugins vary

Example: current CLAUDE.md vs candidate vs none; plugin on/off.

Claim allowed: this configuration helped or hurt this workload.
Agent product

Claude Code vs Codex vs Gemini CLI

Each product keeps its native harness and subscription.

Claim allowed: the whole agent stack worked better for you—not the bare model.
Pipeline

Domain runner + model matrix

Example: enrichment batches, tool loops, judge, labeling, and decision.

Claim allowed: the tested stack produced the better end-to-end product outcome.

1 / OUTCOME

Tests, schema, visual checks, forbidden-file changes, task-specific assertions, final repository state. Objective evidence wins over prose.

2 / INTERACTION

Turns to acceptance, user corrections, rework, approvals, unnecessary changes, tool failures, wall time, compactions. This is where “frustrating to work with” becomes measurable.

3 / HUMAN

Blind pairwise preference plus dimension scores for correctness, judgment, collaboration, restraint, and ship-readiness. Notes remain first-class.

4 / JUDGE

Pairwise, position-swapped judgment over the outcome bundle—not only the final message. Calibrate to your labels and surface cross-judge disagreement for human review.

Recommended default

Use subscriptions for agent-behavior experiments

That is the product experience you actually use. Record CLI version, auth mode, model string, effective config, event stream, quotas/errors, and wall time. Report monetary cost as unavailable or subscription-allocated—not $0.

Use API deliberately

Use APIs for pipeline economics and strict model isolation

The music enrichment back-off needs batch throughput, exact token accounting, response schemas, and true marginal cost. API mode also remains the cleanest lane for narrow prompt/model comparisons.

Provider authentication and automation features change. The implementation should capability-probe each installed CLI and persist the exact --help/version snapshot with every experiment instead of hard-coding assumptions.

Why the command uses ./.venv/bin/evalmine: an editable install creates the console script inside the virtual environment. A bare evalmine works only after activating that environment or installing the package on your shell’s PATH.
Diff

Repository state

Added, modified, and deleted paths plus bounded redacted patches—even when the copy workspace has no .git.

Artifacts

Required outputs

Regular-file presence, non-empty deliverables, and literal required sections in a file or the last response.

Explicit gate

Tests + lint

Direct argument arrays, bounded redacted output, timeouts, exit verdicts, and named workspace side effects.

Tamper evident

Independent envelope

Per-run results and a validation ledger are created once and hashed separately from execution.

Command-validator boundary: the no-provider-runner claim is exact, but an arbitrary manifest-declared test command can still have normal host filesystem and network authority. Evalmine therefore requires --allow-validator-commands and records command side effects; native command sandboxing remains future work.
Blind by default

Stable A/B pairs

Every within-block arm pair appears once. Python bakes the visible-pane-to-run mapping; browser code only looks it up.

Decision evidence

Trajectory, not prose alone

Final response, every turn, tool count, timing, diff, required outputs, and test/lint evidence sit side by side.

Portable human input

Resume, export, import

Plan-scoped browser storage preserves drafts; JSON export/import carries choice, note, actual run, and reveal state.
